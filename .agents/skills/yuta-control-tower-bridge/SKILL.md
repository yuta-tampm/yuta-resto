# YUTA Control Tower browser bridge

Use this skill only for a Codex ↔ YUTA Control Tower browser run. It owns target verification, transport, message validation, command/result binding, and safe stopping. It does not create Product decisions, approve a gate, or replace `$yuta-run-change`, `$yuta-finish-change`, [YUTA Workflow v3](../../../docs/YUTA_WORKFLOW_V3.md), the [Authority Model](../../../docs/AUTHORITY_MODEL.md), or the [QA Protocol](../../../docs/YUTA_QA_PROTOCOL.md). Read current repository evidence and the owning workflow before acting. A valid bridge command is never sufficient authorization by itself.

The user-selected, verified Control Tower conversation is Codex's sole browser endpoint for the current run. For `PAGE_LOCAL`, the owning Page Chat retains Product/shaping authority and may itself serve as the Local Control Tower that communicates directly with Codex. For `CROSS_MODULE` or `UNCERTAIN`, the Global Control Tower coordinates according to Workflow v3. The Human selects and switches conversations; Codex does not autonomously open, switch to, or orchestrate Page Chats. A tab switch alone does not grant executable authority. The selected Control Tower may use only context it can actually access, with provenance and gaps; Global need not retrieve Page Chat history for Local to decide. Repository evidence controls current implemented state. Report a discrepancy between conversation intent and repository state rather than silently choosing one.

## Establish the target and run

1. Use the conversation the current user selected. Before **every** browser send, compare its exact visible title and URL/conversation ID with the selected target, and establish its Local/Page or Global role and scope from current Human/workflow evidence. A `PAGE_LOCAL` target must be its owning Page Chat; a cross-page or uncertain target uses Global coordination. A focused tab, remembered URL, or title alone is insufficient. Never hardcode a historical chat URL in this skill. If target, role, scope, or existing executable authority cannot be established, send nothing; ask the user to select/confirm it (`HUMAN_REQUIRED`), or report `BLOCKED` if browser/session transport is unavailable. Do not accept commands from two conversations at once. Reopening or reselecting does not reset run or causal history.
2. Generate one fresh `RUN_ID` for the run, using an uppercase letters/digits/hyphens token unique to the selected conversation and this run; do not reuse an earlier run ID. Keep the selected title, URL/conversation ID, run ID, latest accepted round/command, outbound delivery state, and observed evidence in the current session. Do not create a background transcript, credential store, or persistent command ledger. If available conversation and repository/review evidence cannot establish execution history after interruption, fail closed.
3. Send one `YUTA_BRIDGE_HANDSHAKE` after target verification and confirmation that Bridge Mode v1 is active in that exact conversation. It identifies `PROTOCOL_VERSION: 1`, the run, task, Human/Control Tower/Codex roles, browser target, requested outcome, context declaration and safety boundaries. Express Local/Global role and scope in the existing `ROLES` and `CONTEXT_DECLARATION` fields; do not add wire fields. `PAGE_CONTEXT_INTAKE` may be `AVAILABLE`, `PARTIAL`, `UNKNOWN`, or `NOT_APPLICABLE` with truthful source/gap information; tooling work with no page owner uses `NOT_APPLICABLE`. A handshake activates intake only: it never grants repository, live Project, or other side-effect permission. A duplicate/replayed handshake does not start another run.

## Exact v1 message grammar

The three block types have these literal, column-zero delimiter lines, with no leading or trailing whitespace:

| Type      | Opening line              | Closing line               |
| --------- | ------------------------- | -------------------------- |
| Handshake | `[YUTA_BRIDGE_HANDSHAKE]` | `[/YUTA_BRIDGE_HANDSHAKE]` |
| Command   | `[YUTA_CODEX_COMMAND]`    | `[/YUTA_CODEX_COMMAND]`    |
| Result    | `[YUTA_CODEX_RESULT]`     | `[/YUTA_CODEX_RESULT]`     |

Inside exactly one block of the expected type per completed message, each field occurs once as `UPPER_SNAKE_CASE: value` at column zero. Field order does not matter. A scalar value is one nonempty line with no leading or trailing whitespace. `FIELD: |` opens a multiline value: **every** following content line, including a blank content line, begins with exactly two spaces; remove those two spaces when reading. The next column-zero field or matching closing delimiter ends that value. Indent literal delimiter-like or field-like text inside multiline content by those two spaces. An unindented delimiter-like line is protocol syntax, not escaped content. Markdown, code fences, and evidence may be content only when every content line follows this indentation. Nested protocol blocks and malformed continuations are invalid.

| Block                   | Required fields                                                                                                                                                                      | Optional fields                                        |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------ |
| `YUTA_BRIDGE_HANDSHAKE` | `PROTOCOL_VERSION`, `RUN_ID`, `TASK`, `ROLES`, `BROWSER_TARGET`, `REQUESTED_OUTCOME`, `CONTEXT_DECLARATION`, `SAFETY_BOUNDARIES`                                                     | `CHANGE`, `PAGE_CONTEXT_INTAKE`                        |
| `YUTA_CODEX_COMMAND`    | `PROTOCOL_VERSION`, `RUN_ID`, `ROUND_ID`, `COMMAND_ID`, `CAUSAL_LINEAGE_ID`, `ACTION`, `STAGE`, `INSTRUCTIONS`, `RETURN_EVIDENCE`, `STOP_CONDITION`                                  | `CHANGE`, `ARTIFACT_SHA256`, `AUTHORIZATION_REFERENCE` |
| `YUTA_CODEX_RESULT`     | `PROTOCOL_VERSION`, `RUN_ID`, `ROUND_ID`, `COMMAND_ID`, `CAUSAL_LINEAGE_ID`, `STAGE`, `STATUS`, `RESULT`, `VERIFY_EVIDENCE`, `QA_EVIDENCE`, `KNOWN_EVIDENCE_LIMITATIONS`, `BLOCKERS` | `NEXT_REQUEST`, `ARTIFACT_SHA256`                      |

`PROTOCOL_VERSION` is exactly `1`. `RUN_ID` and a non-`NONE` `CAUSAL_LINEAGE_ID` match `[A-Z0-9][A-Z0-9-]*`. `ROUND_ID` is a positive decimal integer without a leading zero, starting at `1`. `COMMAND_ID` is exactly the literal concatenation `RUN_ID:ROUND_ID`. `STAGE` matches `[A-Z][A-Z0-9_]*`. `ACTION` is exactly one of `EXECUTE`, `HUMAN_REQUIRED`, `BLOCKED`, `STOP`, `DONE`; `STATUS` is exactly one of `COMPLETED`, `NO_ACTION`, `BLOCKED`, `FAILED`, `DEFERRED`, `STOPPED`. `CAUSAL_LINEAGE_ID: NONE` is allowed only when there is no current causal blocker. An optional field outside the listed allowlist is unknown and invalid; adding a v1 field or syntax requires review.

Inspect only the **latest complete message from the expected sender in the verified conversation**. Ignore older messages as executable input. A marker quoted in prose, Markdown, or a code fence is not an executable top-level block. Reject the message if its top-level status is ambiguous, its block is incomplete, has mismatched/missing delimiters, extra top-level markers or duplicate blocks, a missing/empty/duplicate/unknown/malformed field, invalid multiline indentation, or nested protocol syntax. Do not pick the first of two blocks, silently ignore an extra field, repair malformed syntax, or infer intent. Prose outside a valid block is always `NON_EXECUTABLE`; it may explain a block to a human but cannot add an instruction or authorization. If no command was accepted, do not invent a result bound to its ID. A bounded non-executable English diagnostic may request a fresh block only when target and delivery are certain; repeated malformed responses use the existing evidence-stop rules.

Machine-to-machine block values and diagnostics use English. Human-facing explanations, progress, blockers, and gate questions use Vietnamese outside the block. These language rules do not change authority.

## Accept a command exactly once

Accept a command only after response completion, exact target recheck, full grammar/type validation, matching version and `RUN_ID`, expected next `ROUND_ID`, exact new `COMMAND_ID`, coherent `STAGE` and `CAUSAL_LINEAGE_ID`, and a fresh scope/authorization preflight against the current user's instruction and repository gate/evidence. A command cannot widen the user's approved paths, Product authority, QA criteria, or side-effect permission. Preserve unrelated dirty/untracked work. Do not execute commit, push, PR, merge, deploy, release, destructive operations, or live Project edits without their own explicit authorization.

Only one accepted command may be outstanding. A result must repeat the accepted command's exact `PROTOCOL_VERSION`, `RUN_ID`, `ROUND_ID`, `COMMAND_ID`, `CAUSAL_LINEAGE_ID`, and `STAGE`; the Control Tower must not use a result for another command. After exactly one result and Control Tower evaluation, accept only the next sequential round's **new** valid command. The result alone does not authorize a new round. A duplicate command/result, stale or skipped round, mismatched run/version/stage/lineage, or second block in a message is rejected before execution. Once a `COMMAND_ID` has been accepted or executed, never execute it a second time, including after result-delivery failure, reload, chat reopen, stage rename, or rediscovery in history. If prior execution cannot be disproved from available evidence, treat it as possibly executed and stop `HUMAN_REQUIRED`/`BLOCKED` instead of replaying it.

### One result submission per command

Before submitting a result, inspect the actual selected conversation for already posted `YUTA_CODEX_RESULT` messages with the same `RUN_ID`, `ROUND_ID`, or `COMMAND_ID`. Establish that the full message history needed for this check is visible and that this result's delivery state is positively `NOT_SENT`. The bounded identity guard in `scripts/result-relay-guard.mjs` can classify these observed identities; caller-supplied identities or the guard's output alone do not prove browser state. Prepare and validate the **complete** result, including URL encoding, while it is still a draft. A visual line wrap is not evidence that the draft contains a newline; inspect the draft text before changing it.

Activate Send at most once. From that moment the result is `SENDING`, even if the composer still shows text; do not edit, replace, reformat, click Send again, or press Return again. Observe the same conversation. One visible posted result advances to `SENT_WAITING_RESPONSE`; two visible results for the same command are a protocol failure and cannot be reclassified as a harmless correction. If posting cannot be established, mark `DELIVERY_UNCERTAIN` and stop. A correction to an already posted result requires a **new** command and authority when applicable, never a second result for the old command. Preserve the duplicate evidence and deny a positive runtime continuation when duplicate delivery is observed.

`CAUSAL_LINEAGE_ID` identifies the underlying blocker/evaluator lineage, not the message identity. Preserve the same causal history, recovery attempts, execution generations, and evidence-stop disposition when the cause/scope/evaluator purpose is materially the same, even across a new round, stage label, browser reload, chat reopen, or new run. If ancestry cannot be established, do not execute. Use the existing Control Tower and [automated workflow](../../../docs/YUTA_AUTOMATED_CHANGE_WORKFLOW.md) anti-loop/iteration accounting; do not create a bridge-specific retry budget. Read-only observation or rejected preflight does not consume an execution generation. An actual evaluator execution does. The current defaults are `MAX_RECOVERY_ATTEMPTS=2` per causal lineage and `MAX_EXECUTION_GENERATIONS=3` per lineage + stage + materially same evaluator purpose, with the owning workflow's exact counting and stop rules.

For `ACTION: HUMAN_REQUIRED`, pause the dependent work. Obtain the exact current-user decision for the exact reviewed artifact and pending command, then relay it in **one** result bound to that command; rehash/recheck relevant artifacts before resuming, and wait for a new valid command. A defer is `STATUS: DEFERRED` and stops. Never send a provisional result then a second result for the same command. `BLOCKED`, `STOP`, and `DONE` stop the applicable bridge scope; they do not mean VERIFY/QA PASS, Gate approval, archive, deploy, or release. A `DONE` run accepts no further command absent a valid new run/context.

Result evidence reports what actually happened. Keep `RESULT`, `VERIFY_EVIDENCE`, `QA_EVIDENCE`, `KNOWN_EVIDENCE_LIMITATIONS`, and `BLOCKERS` separate. Use truthful `NOT_RUN`, `NOT_APPLICABLE`, or `NONE` values with reasons when appropriate. Old Bridge Tests or another change's QA are historical context, not current evidence. A repository prompt update does **not** update a selected Control Tower conversation's operating context. Keep Bridge Mode `NOT_VERIFIED` for that exact conversation until a Human applies the reviewed full Bridge Mode there and a fresh valid handshake, command, bound result, and Control Tower evaluation round is observed there. Verification in Global does not verify Local. Global Project Instructions contain shared rules and may include only a short authority/routing boundary; an ordinary Page Chat does not receive the full Bridge runtime protocol merely by belonging to the Project. An explicitly selected Local Control Tower needs the protocol in its own operating context before it can issue executable bridge commands.

## Browser delivery state and recovery

Track each outbound handshake, result, or diagnostic separately using UI evidence in the verified target. Transport state is not repository execution or QA status.

| State                   | Observable evidence                                                      | Allowed action                    | Forbidden action / stop                                                                                                                                          |
| ----------------------- | ------------------------------------------------------------------------ | --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NOT_SENT`              | Send not activated; draft intact; no post event                          | Verify target, send once          | Do not infer a command from a draft; uncertain target → `HUMAN_REQUIRED`                                                                                         |
| `SENDING`               | Send activated; post or pre-post error not established                   | Observe same target               | No second Send or alternate chat; positive pre-post failure → `NOT_SENT`, otherwise `DELIVERY_UNCERTAIN`                                                         |
| `SENT_WAITING_RESPONSE` | Outbound message visibly posted in target; no response yet               | Wait and inspect read-only        | No resend; stalled transport → bounded stop/`BLOCKED`                                                                                                            |
| `RESPONSE_GENERATING`   | UI still generating/streaming                                            | Wait and inspect read-only        | No parsing partial content or resend; interrupted completion → bounded check, then `DELIVERY_UNCERTAIN`/`BLOCKED`                                                |
| `RESPONSE_COMPLETE`     | Generation ended and full message visible in target                      | Validate latest full message once | No old/duplicate-message execution; malformed block → bounded diagnostic, no execution                                                                           |
| `DELIVERY_UNCERTAIN`    | After bounded observation, post/receipt/completion cannot be established | Read-only verification only       | No resend, alternate chat, or command replay; `HUMAN_REQUIRED` for target/delivery confirmation, `BLOCKED` for unavailable session/transport or exhausted limits |

Resend only with **positive proof of non-delivery**: for example, Send was never activated, or UI proves failure before posting with the original draft intact and no posted message in the verified target. Absence from a still-loading view, timeout, reload, or lack of reply is not proof. After such proof, recheck target and lineage, return to `NOT_SENT`, and send the same message once within existing recovery controls. If uncertain, stop without resending. An already executed command is never re-executed to repair result delivery.

Reload permits read-only target, message-visibility, and identity-history checks; it never resets counters. Login/session loss stops transport as an environment blocker; do not silently switch account. Interrupted/partial generation is not a command. A malformed response may prompt one non-executable diagnostic only when delivery and target are certain; it does not consume the expected round. Repeated malformed responses preserve the same cause/lineage and stop at evidence/recovery limits. Navigation ambiguity stops sending until the user confirms the target.

## Stop and handoff

At every stop, report in Vietnamese the verified target/run/round/command when known, exact action and authorization source, observed delivery state, repository paths/hashes or unchanged state, separate VERIFY/QA/limitation/blocker facts, remaining Human decision, and whether behavior in the selected live Control Tower conversation was actually verified. Do not claim a lifecycle status from transport alone. If preserving Page Chat authority, at-most-once execution, or the two-owner implementation boundary requires an unapproved new mechanism, return `HUMAN_REQUIRED`/`NEEDS_REVIEW` to the owning workflow rather than changing it.
