# Federated Control Towers — single-host orchestration

Phase 1 supplied static preflight; Phase 2 supplied the local lock, journal, budgets and authority proof foundation. Phase 3 added synthetic `FED-QA-*` orchestration. The targeted LIVE_TOWER_SELECTION correction added typed authority checks; the built-in-browser binding correction supplies one long-lived held-lock request/continuation transaction. Caller-supplied metadata cannot prove browser origin. A separate exact Human live-selection gate and actual Codex browser round remain required before a real tower can become executable. This implementation-correction gate does not authorize selecting or activating a real tower, sending a browser probe, reassessing T18/T19, or running Q01–Q35. Every synthetic action returns `ExecutableAuthority=false`; a synthetic `ACTIVE` snapshot is test data.

## Authority and mode

- The existing [Bridge v1 skill](../yuta-control-tower-bridge/SKILL.md) remains the independent single-gateway baseline. Do not modify its wire grammar, owner files, or paused QA evidence. Federation is a separate explicit mode; a context starts in `BRIDGE_V1` and may select `FEDERATED` only through a current-user decision or reviewed workflow binding the execution context, host, checkout, and scope.
- YUTA Workflow v3 remains authoritative. For `PAGE_LOCAL`, the owning Page Chat retains Product and shaping authority. A `PAGE_CONTROL_TOWER` is an execution transport role for that page, not a new Product or Human Gate authority. For `CROSS_MODULE`, `UNCERTAIN`, and shared/foundation work, the `GLOBAL_CONTROL_TOWER` coordinates under Workflow v3 without inventing missing Page Product decisions. Codex remains the executor and evidence collector.
- A role, activation record, handoff, handshake, chat message, or matching title does not authorize Apply, Product decisions, Human Gates, side effects, commit, push, PR, merge, deploy, release, sync, or archive. Recheck the exact current-user decision, artifact hashes, and scope for each gated action. Machine protocol and diagnostics use English; Human-facing updates use Vietnamese.

## Static identity contract

- `EXECUTION_CONTEXT_ID` is a unique uppercase token for one Human/workflow-defined work context. It is distinct from `RUN_ID`; never recycle either to switch conversation instances.
- `CONTROL_TOWER_ROLE` is exactly `PAGE_CONTROL_TOWER` or `GLOBAL_CONTROL_TOWER`. A Page role has `CONTROL_TOWER_SCOPE: PAGE_LOCAL` and exact `OWNING_PAGE_CHAT_ID`. A Global role has `OWNING_PAGE_CHAT_ID: NONE` and a cross-module, uncertain, cross-page, shared, or foundation scope. Do not infer role, owner, or scope from title.
- Logical `TOWER_ID` is the structured tuple `(CONTROL_TOWER_ROLE, CONTROL_TOWER_SCOPE, OWNING_PAGE_CHAT_ID | NONE)`. Runtime `CONTROL_TOWER_INSTANCE` is the exact conversation ID within an exact Project ID; `(TOWER_ID, PROJECT_ID, CONTROL_TOWER_INSTANCE)` is the runtime identity. Title is comparison metadata only.
- A later active-tower operation must verify exact Project, visible title, URL and conversation ID before every send. Wrong, ambiguous, or unproven identity means send nothing. Phase 1 performs no browser target verification or send.

Contention, uncertain execution/delivery, journal-ahead recovery, crash artifacts, competing authority, wrong context or any mutation parameter blocks. The observation is a point-in-time preflight; it does not authorize transfer, preserve lock ownership after return or replace the later transaction's under-lock recheck.

Only authorized synthetic Phase 2/3 actions may create ignored `tmp/yuta-federated-control-towers/FED-QA-*/` records. The helper holds an exact `FileStream(..., FileShare.None)` handle across each local transaction and performs read-only reconciliation after a restart. A released process handle does not erase the journal, and a surviving lock file does not grant authority. Never delete a lock to recover. Missing/corrupt/orphan state, uncertain probe/command/delivery or unsupported host/checkout blocks dependent work. Keep fixture records for evidence; cleanup needs separate authorization.

3. Use the unchanged Bridge v1 parser and grammar for a complete read-only handshake → command → result → Control Tower evaluation. For a transfer it also consumes one exact unused immutable handoff. The probe consumed round 1, so the first later command on that run must be round 2. ## Phase 3 ordered transfer and recovery

- Stop dependent work and prove no pending execution or delivery. Commit `ACTIVE→FENCING` before `FENCING→TERMINAL|REVOKED`; the old run is revoked at the durable fence commit. A Global-to-Page request for any other target or context, owner substitution, same-conversation transfer and same-run switching stop. ## Targeted live-selection correction — built-in browser transaction

- `InitializeLiveContext` may create only an `INACTIVE` local genesis for an exact non-`FED-QA-*` context after an independently authorized live setup. It does not select a tower. `RunLiveSelection` requires the exact `DECISION_ID` of a reviewed `LIVE_TOWER_SELECTION` record and verifies the existing pre-decision descriptor → accepted Human Gate result → approval record → semantic decision record chain. Its private version-2 mapping accepts only `APPROVE_LIVE_TOWER_SELECTION`; a caller string, matching title, fixture result, handoff, or this implementation-correction gate cannot substitute. Never invoke either live action from the current correction authorization.
- `RunLiveSelection` takes the existing exclusive lock after validating the exact reviewed Human selection chain. It consumes that decision once, reserves a fresh run and round-1 `PROBE_INTENT`, then emits one bounded `CODEX_BUILT_IN_BROWSER_READ_ONLY_ROUND` request and waits on stdin **without releasing the lock**. Codex performs the browser action using its built-in browser, checks the exact visible target before every send, applies unchanged Bridge v1 grammar, and returns a canonical `CONTROL_TOWER_EVALUATION_INPUT` bound to the decision, context, lineage, tower, run, epoch, command and probe intent. The helper records the attributable result or uncertainty, flushes and reads back the state, then releases the lock. Invoke this live action only after the separate Human live-selection/RC1 gate; the current correction gate is insufficient.
- The stdin continuation is bounded external evaluation input, never independent proof of browser origin, a Human Gate, or RC1/RC2 PASS. `TRANSPORT_SOURCE=CODEX_CUA_ACTUAL_UI` and other caller provenance markers are rejected. Codex and Control Tower must independently retain actual browser observation and evaluation evidence. A matching local JSON object or synthetic test cannot establish that evidence. Never persist transcript text, cookies, tokens or session data.
- If the browser response, target, delivery or result is missing, uncertain, malformed or mismatched, send no replacement command. The helper durably classifies uncertainty and refuses executable authority. A process crash leaves an accepted probe intent uncertain on reconciliation; a consumed Human decision and old run remain non-reusable. Manual recovery requires a new bounded decision after evidence review, never timeout takeover.
- `TerminalizeUncertainLiveSelection` is a bounded non-executing recovery for an exact `ACTIVATING` live run whose result delivery and execution remain uncertain. It requires the current record hash, consumed decision ID, reserved run and command under the existing exclusive lock. It commits `ACTIVATING→TERMINAL`, marks that run terminal, and journals the blocker while preserving uncertain delivery/execution, the consumed proof, accepted command identity, budgets and history. It does not clear the blocker, grant another run, or make the old authority or command replayable. A fresh live selection still needs a separate reviewed Human decision and an independently valid source state.
- The round-164 `PrepareHistoryPreservingRetry` correction is limited to the exact terminal uncertain parent and one fresh run in the **same** execution context and causal lineage. Under the existing lock it verifies the old consumed proof and pending probe, then journals one `RETRY_GENESIS` whose `PREVIOUS_RECORD_HASH` is the old immutable terminal hash. The old journal revision retains `DELIVERY_UNCERTAIN` / `EXECUTION_UNCERTAIN`, old command and consumed authority; the new revision's `NOT_SENT` / `NONE` slots describe only the fresh retry. Budgets, blockers, run history and consumed proofs are unchanged. A second transition or old command/authority replay is rejected. This is non-executing state preparation, not a live selection or browser send.
- A later retry selection requires a fresh reviewed `LIVE_TOWER_SELECTION` descriptor, exact accepted Human Gate and new decision ID. Its target run must equal the `RETRY_GENESIS` target and its tower must be the exact prior Control Tower conversation. Only that same-tower terminal retry may omit a cross-instance handoff; ordinary Page/Global rotation and escalation still require the existing handoff. No authority or live RC1/RC2 is granted by the retry genesis or review packet.
- For Page or Global rotation and Page→Global escalation, an exact new `LIVE_TOWER_SELECTION` decision and fresh target `RUN_ID` are required. The old `ACTIVE` run is fenced and terminal before an immutable handoff is persisted; budgets, freeze state, consumed proofs, lineage, blockers and evidence stop carry without reset. Page-sourced handoff defaults Page-context intake to `UNKNOWN` with an explicit gap until a separately authorized, attributable Page context handoff is established. `UNKNOWN` cannot authorize missing Product decisions. The handoff cannot approve a target or replace the fresh probe. Replaying the decision, handoff or probe blocks.

## Phase 2 foundation retained; live execution remains separately gated

- The helper implements local exclusive locking, canonical activation schema, immutable hash-chained journal, `Flush(true)` plus same-volume replace/create, read-back, monotonic revision/epoch, exact run/instance binding, and read-only non-executing restart reconciliation. Historical Phase 2 fixtures deliberately prevented any real executable `ACTIVE_CONTROL_TOWER`. Conflicting or uncertain claims mean zero executable authority; only separately authorized live operation and QA can establish observed single-active runtime behavior.
- The old tower loses executable authority at the verified `ACTIVE→FENCING` commit. A new tower gains it only at the verified `ACTIVATING→ACTIVE` commit after old terminal state, complete unused handoff, exact target check, and a fresh read-only protocol probe. No direct `ACTIVE→ACTIVE` transfer or same-`RUN_ID` instance switch is permitted.
- Synthetic transfer reserves a fresh target `RUN_ID` after the old fixture run is terminal. Preserve `CAUSAL_LINEAGE_ID`, recovery/evaluator budgets, blockers, evidence-stop state, approvals and hashes. Immutable handoff content is bound to a journaled hash, consumed once and never authorizes an action. The local ledger records accepted intent before a synthetic read-only no-op, then executing/outcome; missing outcome becomes `EXECUTION_UNCERTAIN`. Stale run/epoch/instance/round, duplicate command, superseded or consumed handoff, and uncertain delivery must not be replayed.
- Direct cross-chat retrieval is optional. An explicit Human-authorized read-only Page handoff may supply context without transferring Product authority. `UNKNOWN` never means no earlier requirement exists. Repository evidence owns current implemented state; report discrepancies.
- Existing Bridge v1 handshake, command and result framing, identity, delivery uncertainty, and at-most-once rules remain unchanged. No federation role/epoch field is added to v1 wire blocks. Historical Phase 3 and this correction send no federation browser traffic; local synthetic probe records are not live handshake or Browser QA evidence.
