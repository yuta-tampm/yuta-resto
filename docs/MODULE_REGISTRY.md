# YUTA Module Registry

Visibility: Engineering

Owner: YUTA product and engineering

Proposed: 2026-08-26

## Purpose

This registry is the central index of YUTA products, runtimes, modules, and
bounded capabilities. It identifies where to read next, where implementation
evidence lives, who owns runtime and data, which important relationships exist,
and how current evidence maps to the five approved lifecycle dimensions.

The registry is not a product specification and does not replace Product
Knowledge, approved OpenSpec specifications, tracked code and tests, executable
schemas, or dated operational evidence. Every status below follows
[`AUTHORITY_MODEL.md`](AUTHORITY_MODEL.md) and
[`LIFECYCLE_STATUS_MODEL.md`](LIFECYCLE_STATUS_MODEL.md). A repository status
does not prove that the same version is deployed.

## Registry conventions

- **Product / Runtime** is a major independently owned product or execution
  boundary.
- **Module** is a meaningful business or platform function within a product or
  runtime.
- **Capability** is a bounded slice that needs its own status because its
  implementation, owner, environment, or production gate differs.
- **Primary Knowledge Source** points to the most specific current Product
  Intent or architecture source. It is not replaced by this registry.
- **Implementation Evidence** points to tracked code, schemas, contracts, or
  tests that support repository Implemented State.
- **Data Owner** names the persistence boundary. `N/A` means the bounded scope
  has no persisted business data; `NEEDS REVIEW` means ownership is unclear.
- **Runtime Owner** names the application or service that executes the
  capability.
- **Related Modules** records only important dependency or ownership links.
  `A -> B` means A depends on or reads from B.
- **Review Marker** is an evidence/review signal, not a lifecycle status. Its
  allowed values are `OK`, `UNVERIFIED`, `CONFLICT`, and `NEEDS REVIEW`.

Where evidence cannot support a canonical value, the status is `—` and the
review marker explains that the row needs verification or review. Statuses are
scoped only to the exact capability stated in the row.

## OpenSpec position

YUTA's normative main-spec role is enabled under the approved
[OpenSpec Normativity Policy](OPENSPEC_YUTA_NORMATIVITY_POLICY_REVIEW.md).
Successfully gated, synced, and validated main specs are the primary authority
for precise observable behavior inside accepted durable boundaries. This
registry remains the lifecycle, ownership, relationship, and evidence-routing
index; it does not copy specification content.

The main-spec count is currently zero, so no capability-specific spec link or
registry row is added by this activation. Add a spec link only when an approved
normative main spec actually exists for that bounded capability.

OpenSpec changes, unsynced delta specs, failed or partial sync output, and
unvalidated main-spec results are non-normative. Creating, applying, verifying,
syncing, or archiving work does not by itself change any registry status. A
status changes only after the corresponding Product Intent, repository,
environment, readiness, or external-dependency evidence is separately reviewed
under the lifecycle model.

## Adoption / maintenance rule

1. Keep this registry as a central index, not a source of business logic.
2. Add or update the bounded row when a meaningful module or capability is
   introduced.
3. Update source links and ownership only after the relevant decision is
   approved.
4. Update the five lifecycle dimensions independently and retain the evidence
   scope.
5. Do not promote status automatically from OpenSpec apply/archive, a code
   merge, or another status dimension.
6. Use `CURRENT_STATE.md` as a summary, but link a more specific authority when
   one exists.
7. When evidence conflicts, keep `CONFLICT` or `NEEDS REVIEW`; do not select the
   most convenient source.
