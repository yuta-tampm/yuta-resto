## Mode, role, scope, and authority

This protocol applies only when a task selects `CT_BRIDGE` or `HUMAN_CT_BRIDGE` and separately
selects federation under its existing exact authority contract. It is not a
mandatory task coordinator. Codex owns repository discovery, shaping and
coordination in every collaboration mode; its executor role below describes
the federation transaction only. Routine project gates follow
[the collaboration/delegated-review policy](../YUTA_AUTOMATED_CHANGE_WORKFLOW.md#task-collaboration-and-delegated-review),
not CT approval. Live selection, transfer, recovery and activation still require
their existing actual Human authority chain and live evidence. This policy
update changes no recorded activation, T18/T19 result, pending Q01–Q35 QA,
runtime helper or authority proof.

An execution context begins in `BRIDGE_V1`. `FEDERATED` requires an explicit current-user or reviewed workflow selection tied to one `EXECUTION_CONTEXT_ID`, one Windows host, one canonical local NTFS checkout, and an approved scope. The context ID is a unique uppercase token, not a `RUN_ID`.

`CONTROL_TOWER_ROLE` is `PAGE_CONTROL_TOWER` or `GLOBAL_CONTROL_TOWER`. A Page tower is scoped to one owning Page Chat and `PAGE_LOCAL`; that Page Chat continues to own Product/shaping intent. A Global tower coordinates `CROSS_MODULE`, `UNCERTAIN`, cross-page, shared, and foundation work under YUTA Workflow v3. Neither tower role grants Product decisions, Human Gate approval, new side-effect authority, or a recovery-budget reset. Within the federation transaction Codex executes and collects evidence; it remains the project coordinator under the selected collaboration mode.

The logical `TOWER_ID` is the structured tuple `(CONTROL_TOWER_ROLE, CONTROL_TOWER_SCOPE, OWNING_PAGE_CHAT_ID | NONE)`. `CONTROL_TOWER_INSTANCE` is an exact ChatGPT conversation ID within the selected Project. The runtime tower identity adds exact Project and instance IDs to the logical tuple. A title is checked before sending but cannot identify or authorize a tower by itself. Exact visible title, Project ID, URL, and conversation ID must match before **every** future browser send. Wrong or uncertain identity means no send.

## Single-active and local state contract

Only one executable `ACTIVE_CONTROL_TOWER` may exist for one supported execution context. A conflicting or uncertain active claim means zero executable authority. The approved boundary is **one local Windows host, one canonical NTFS checkout, and all executors using one approved helper and context path**. A different checkout or host is unsupported; there is no distributed or cross-host atomicity guarantee.

The bounded `ReconcileLiveReadOnly` action inspects the exact foundation context under its existing `FileShare.None` lock before preparing a Human review packet. It creates no lock file or runtime state, refuses recovery writes and uncertain or competing authority, and releases the lock after a point-in-time observation. A later authorized transfer must reacquire the lock and recheck the source; this read-only result cannot grant or preserve executable authority.

The ignored state root is `tmp/yuta-federated-control-towers/<EXECUTION_CONTEXT_ID>/` with an exact `lock`, `activation.json`, immutable `journal/<REVISION>.json`, and immutable `handoffs/<HANDOFF_ID>/handoff.json`. The helper uses a held `FileStream` with `FileShare.None`, hash-chained revisions, `Flush(true)`, same-volume replace or create, read-back and fail-closed reconciliation. Synthetic `FED-QA-*` actions always return `ExecutableAuthority=false`. Live selection requires a separate exact Human selection gate and a browser round; this implementation-correction gate authorizes neither. A surviving lock file, PID, host label, timestamp, chat message or Markdown alone is not ownership proof.

The old tower is revoked at a verified `ACTIVE→FENCING` durable commit. A new tower could become executable only at a later verified `ACTIVATING→ACTIVE` commit, after old terminal/revoked state, complete unused handoff, exact target verification, and one valid fresh live read-only handshake→command→result→evaluation probe. Between commits, no tower may execute dependent work. No direct `ACTIVE→ACTIVE` transfer is allowed. The current non-live tests exercise these transitions only with synthetic, non-executable records; they do not prove live runtime transfer.

## Handoff, lineage, and command safety — local fixture implementation

Every instance transfer reserves a fresh target `RUN_ID` only after the old run is terminal; switching instances within the same `RUN_ID` is prohibited. Immutable, integrity-checked handoff evidence preserves source and target role/scope/instance, exact conversation IDs, terminal/delivery/execution state, last run/round/command identity, `CAUSAL_LINEAGE_ID`, recovery and evaluator budgets, evidence-stop state, unresolved blockers, Human approval references, artifact hashes, and Page-context provenance/gaps. A handoff does **not** approve Product decisions, Apply, Human Gates, or side effects.

The Phase 2 local ledger binds `COMMAND_ID→RUN_ID→RUN_BINDING→ACTIVATION_EPOCH→TOWER_ID/instance` under the supported lock for a synthetic read-only no-op. It persists `COMMAND_ACCEPTED` before the no-op, then `COMMAND_EXECUTING` and one attributable outcome. Missing outcome is `EXECUTION_UNCERTAIN`, never a reason to run that command again. Handoffs reserve a fresh target run in terminal state, retain their immutable hash in the journal, and are consumed once; a handoff is not authorization. Stale run/epoch/instance/round, duplicate intent, drifted or consumed handoff, malformed or prose-only protocol content, and result/command mismatch are non-executable. Timeout, reload, missing response, or tower switch alone cannot prove non-delivery or authorize resend. Browser/process restart does not reset causal lineage or recovery budgets.

The existing Bridge v1 `YUTA_BRIDGE_HANDSHAKE`, `YUTA_CODEX_COMMAND`, and `YUTA_CODEX_RESULT` wire grammar and version 1 identity rules remain unchanged. Federation adds no role, scope, or epoch wire field and no new executable block. Machine-to-machine fields and diagnostics remain English; Human-facing updates remain Vietnamese.

## Page context and Human Gates

`PAGE_CONTEXT_INTAKE` records `AVAILABLE`, `PARTIAL`, `UNKNOWN`, or `NOT_APPLICABLE` with the owning Page Chat ID, source, question scope, completeness, and gaps. Direct cross-chat retrieval is optional and cannot be assumed reliable. A Human-authorized read-only handoff may carry Page Product/shaping context; it does not transfer Page authority or authorize implementation. `UNKNOWN` does not prove that no prior requirement exists. Repository evidence is authoritative for current implemented state; discrepancies with Page Product intent are reported, not resolved by assumption.

Human selects exact tower conversations and decides all actual Human Gates on reviewed artifact bytes/scope. Routine delegated project gates use the canonical independent-review procedure; it grants no federation activation authority. A live-context update and one fresh read-only protocol round are needed per target before its live mode can be called verified. A role label, handoff, activation record, or protocol result never self-approves a gate. The Phase 2 local foundation did not itself activate a tower; the later Human-authorized Global tower selection and live round are recorded in `04m`.

## Privacy, limits, and future acceptance

Local records may retain only bounded Project/conversation ID, title and URL comparison metadata, owning Page Chat ID, role/scope, approval and artifact/evidence references and hashes, lineage/budget/blocker identities, and Page-context completeness/gap metadata. Do not persist credentials, secrets, cookies, tokens, sessions, authentication material, full transcripts, unrelated private chat content, or personal customer data. Cleanup cannot erase evidence or resolve uncertainty by deleting a lock.

If the Design requires another host, checkout, owner path, wire protocol, credential store, provider API, additional browser/filesystem/network permission, Product authority, or Workflow v3 rule, stop for `NEEDS_REVIEW`. Missing or ambiguous lock, state, target, delivery, outcome, approval, or lineage blocks dependent work. Implementation checks cannot prove single-active runtime safety. Fresh T19 Formal VERIFY and Federated Browser QA Q01–Q35 remain independent and `NOT_RUN`; Bridge v1 Browser QA remains paused and separate.
